Database-to-model flow

The database layer first serves catalogue-convention geometry data, then the model-loading layer translates to the mirror convention used by the JAXVacua physics objects.

Remote parquet repositories
cy-database TDF and CICY catalogues with sharded geometry, GV, and conifold data.
kklt-vacua-database Curated TDF subset indexed by conifold class and run provenance.
Local cache Project-local parquet shards, optional offline mode, and LRU shard reuse.
Catalogue-convention I/O
CYDatabase Common query, cache, shard-loading, and batch-loading machinery.
TDFDatabase Kreuzer-Skarke models addressed by ks_id and triang_id.
CICYDatabase Complete-intersection models addressed by cicy_id.
Convention boundary: catalogue columns use the original geometry labels; LCS loaders expose mirror-convention h11 and h12.
Mirror-convention model construction
LCSDatabase Builds lcs_tree data and ready-to-use FluxVacuaFinder models.
KKLTDatabase Loads the KKLT-oriented subset with conifold-class provenance.
Batch and sample APIs Iterate, query, and sample compatible models for scans.
Downstream use
Flux-vacua search Pass models to JAXVacua solvers and samplers.
VacuaWriter Store and designate vacuum solutions with model metadata.
Cross-package pipelines Feed stabilisation and axion workflows from a common model source.
